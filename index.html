보내는 작업

요금·취소·메시지는 바로 보내지 않고 대기열에 먼저 기록해요. 채널마다 결과를 따로 남기고, 실패하면 유형에 맞게 다시 보내요.

대기열

최근 작업부터 보여요. 칸마다 채널 한 곳의 결과예요.

    실패하면 이렇게 해요

    • 인증 실패

      자동으로 다시 보내지 않아요. 같은 키로 몇 번을 보내도 실패해서요. 바로 알림을 보내고, 연결을 다시 한 뒤 재처리해요.

    • 호출 제한 429

      Channex는 숙소당 1분에 요금·제한 10번, 재고 10번까지 받아요. 넘으면 1분 쉬고 다시 보내요. 데모에선 6초로 줄였어요.

    • 타임아웃

      2초, 4초, 8초로 간격을 늘리며 다시 보내요. 같은 멱등 키라 두 번 반영되지 않아요.

    • 응답 유실

      보냈는데 답이 없으면, 다시 보내기 전에 채널 쪽 값을 먼저 읽어요. 이미 들어가 있으면 다시 보내지 않아요.

    • 5번 넘게 실패

      '실패'로 멈추고 알림을 보내요. 대기열에서 버튼 하나로 재처리해요.

    호출 제한 숫자는 Channex 공개 문서(Rate Limits)를 10/22에 확인한 값이에요.

    웹훅 수신

    Channex 알림은 순서가 바뀌거나 두 번 올 수 있어요. 이벤트 ID를 먼저 저장하고 바로 응답한 뒤 처리해서, 같은 알림은 한 번만 반영해요.

    받은 알림

    줄을 누르면 저장된 내용을 볼 수 있어요. 손님 정보와 키는 가려서 남겨요.

    웹훅 연결

    기록 대조

    우리 PMS 기록과 채널 쪽 값을 30분마다 비교해요. 요금·재고는 PMS 기준으로, 예약은 채널 기준으로 맞춰요.

    서로 다른 곳

    예약 취소와 재고 복원

    취소되면 그 날짜의 방을 되돌려요. 사장님이 직접 막아 둔 날과 다른 손님 예약은 건드리지 않고, 같은 취소가 두 번 와도 한 번만 되돌려요.

    온돌 패밀리 · 방 2개

    예약 A 김*진(Airbnb) 11/14~11/17 3박, 예약 B 박*우(Booking.com) 11/15 1박

    눌러서 확인해 보기

      기존 기능 보호

      예약 불러오기처럼 지금 잘 되는 부분은 그대로 두고, 고친 부분만 하나씩 켜요.

      하나씩 켜기

      끄면 바로 기존 코드로 돌아가요. 다시 배포하지 않아도 돼요.

      고치는 순서

      1. 지금 동작을 테스트로 먼저 묶어요

        예약 불러오기, 생성·변경·취소, 같은 알림 반복과 역순 도착. 고치기 전에 지금 결과를 그대로 기록해 두고, 고친 뒤 같은지 비교해요.

      2. 운영 데이터는 읽기 전용 사본으로 재현해요

        손님 이름과 연락처를 가린 사본만 써요. 운영 DB에는 쓰기 권한 없이 들어가요.

      3. Channex 시험 계정에서 먼저 보내 봐요

        실제 숙소와 연결되지 않은 시험 계정이라 손님 예약이 생기거나 바뀌지 않아요.

      4. 운영에는 기능 하나씩 켜요

        요금, 취소, 메시지 순서로 켜고, 켤 때마다 배포 전후 점검표를 확인해요.

      5. 이상하면 바로 되돌려요

        기능을 끄거나 Vercel 이전 배포로 되돌려요. 백업 복구도 시험 환경에서 한 번 해 봐요.

      이 화면은 제안용 예시예요. 숙소 이름, 손님 이름, 예약 번호, 시각은 모두 가상이에요. 실제 작업은 대표님 코드와 Firebase 구조를 본 뒤에 맞춰요.

      운영 연결은 잠겨 있어요

      이 데모는 시험 환경에서만 움직여요. 실제 작업에서도 운영 전환은 아래를 마친 뒤에만 해요.

      • 시험 환경에서 자동 테스트를 모두 통과
      • 대표님이 결과를 보고 확인
      • 운영 화면에는 실패 섞기 같은 시험용 버튼을 숨김
